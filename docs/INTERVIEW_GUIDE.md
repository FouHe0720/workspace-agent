# 面试阅读与追问

先按 `tools.py → sandbox.py → models.py → runtime.py → store.py` 阅读，再看 `planning.py` 与 MCP 两端。下面的回答对应当前实现；测试与实测状态以 [VALIDATION.md](VALIDATION.md) 为准。

## 1. Agent 与 Workflow 有什么区别？本项目是哪一种？

Workflow 通常由程序决定步骤、分支和执行顺序；Agent 通常让模型根据目标与观察选择后续行动。二者是控制权的区别，不取决于是否使用某个框架。

本项目有手写 Agent Loop：真实模型收到目标、工具 Schema 与历史 observation，自行提议下一轮 `tool_calls`。外层权限、预算、停止条件和初始四步骨架由代码控制。

离线 `ScriptedMockModel` 则是确定性的演示 Workflow，通过已经追加的工具结果选择下一步，不能解释任意自然语言目标。它可以验证真实工具和循环接线，也能在笔记变化后提取本次读到的内容；这不证明真实模型的规划、概括或泛化质量。`planning.py` 使用固定四步与 observation 调整，没有通用 planner。

追问：如果所有分支都能事先列举，为什么一定要引入模型？应比较目标变化频率、工具选择空间、输出不确定性、错误成本和验证成本，而不是因为有 LLM 就把确定性流程交给它。

## 2. Function Calling 是模型直接调用 Python 吗？

模型返回函数名称、调用 ID 与 JSON 参数；它没有执行权限。`OpenAICompatibleModel` 解析兼容接口的响应，校验调用结构、唯一 ID、参数 JSON 以及请求/响应大小。`AgentRuntime` 记录调用意图，再把参数交给 `ToolDispatcher`。

Dispatcher 的白名单只包含六个工具，Pydantic 采用严格类型和禁止额外字段。例如 `max_results="5"` 不会自动变成整数，`overwrite="true"` 也不会变成布尔值。非法名称不会触发动态导入或任意 Python 函数。执行后的 `ToolResult` 作为 tool 消息追加回历史，下一轮模型才能观察结果。

追问：JSON Schema 约束了什么？它描述输入契约，模型和客户端可以使用它，但服务端仍必须验证；Schema 不自动完成目录授权、覆盖批准、运行预算或副作用校验。

## 3. 手写 Loop 的关键不变量是什么？

第一，模型只是提议操作。第二，每个工具在执行前必须有持久化调用意图；执行后才记录结果。第三，工具内容保持 tool 数据角色，不能改变系统策略。第四，每轮和每次调用都检查预算。第五，不确定副作用不自动重放。

同一模型响应里的多个工具当前顺序执行。运行时保存 assistant 的调用列表，再为每个请求建立 `ToolEvent`，运行工具、记录 observation、更新计划，继续下一轮。重复调用 ID 被拒绝；重复工具与参数的调用受到循环检测约束。

追问：能否直接并发执行一批工具？独立只读操作较容易；写操作可能互相依赖，完成顺序、状态检查点、错误后停止及调用预算都需要新的定义。当前顺序模型减少这些状态组合。

## 4. SQLite 持久化是否意味着 exactly-once？

不能。SQLite 事务原子保存的是 JSON 快照，不是 SQLite 与外部文件之间的分布式事务。写操作可能已落盘，但进程在保存结果前退出；也可能在原地写入途中被终止，留下部分文件。

`RunStore.recover()` 只把遗留的 `running` 快照恢复成明确的 `interrupted` 状态，记录尚无结果的调用，提醒操作者核对磁盘。它不自动续跑，不把 `result=null` 解释为“未执行”。新 run 默认禁止覆盖，也能降低重复请求误覆盖的风险。

todo 状态带格式标记，写入前用旧内容 hash 检查冲突；普通文件写入仍要求明确覆盖批准。这些措施不等于跨进程事务、任意工具幂等性或 exactly-once。

追问：以后如何加强？可以为可幂等操作设计幂等键、用临时文件与原子替换改善单文件提交，再设计副作用账本及人工确认恢复；仍要定义提交后回执丢失的语义。

## 5. 错误恢复和重试在哪里实现？

错误首先是结构化 observation：包含 `code`、安全消息和 `retryable`。缺失文件与参数错误会被记录到 `plan_revisions`，下一轮模型可以搜索候选路径或修正参数。离线演示用不存在的笔记路径展示前一种修复。

模型超时或可重试的模型错误，在预算允许时最多额外重试一次。工具没有通用的自动重试循环；只读工具超时交给下一轮决策，仍受总次数和重复限制。越权、权限拒绝、覆盖拒绝以及写工具超时会终止运行。写超时不能简单当作“没有发生”，因为文件可能已改变。

追问：`retryable=true` 为什么不意味着立即自动重试？它只说明可能存在恢复路径；是否重试还取决于幂等性、剩余预算、前次副作用和错误上下文。`STATE_CONFLICT` 需要重新核对状态，不能无条件覆盖。

## 6. MCP 增加了什么？为什么使用底层 Server？

原生 dispatch 是进程内 Python 调用；MCP 提供标准的工具发现、Schema 描述、调用消息和 transport，使另一个进程中的 Client 可以访问同样的工具。

本项目使用官方 Python SDK v2 的底层 `Server` hooks，发布四个文件工具。`on_list_tools` 返回同一 Pydantic Schema，`on_call_tool` 将原始参数交给同一 Dispatcher。这样不会因为高层函数包装的类型转换，使 MCP 接受原生入口拒绝的字符串整数或额外字段。MCP 的结构化结果、文本 JSON 与 `is_error` 保持一致。

Client 通过固定 Python 模块启动独立 stdio Server，初始化后发现工具并逐项调用。`mcp-demo` 比较六个成功、预览与拒绝案例；这是实际协议传输比较，不是两个本地函数互相比较。

追问：stdio 有什么限制？它适合本地父子进程连接，stdout 必须保留给协议，日志应走 stderr。当前没有实现远程服务、跨用户授权、HTTP transport 或生产级并发吞吐测试。MCP 是接口协议，不自动赋予安全边界。

## 7. 沙盒为何不能只使用 `Path.resolve()`？还剩什么竞态？

`resolve()` 能检查当时的真实路径，但“检查路径”和“打开文件”是两个时刻。若中间有人把路径换成指向外部的符号链接，仅做一次字符串前缀检查无法防止后续访问外部文件。

这里先明确授权已有根目录，再固定根目录描述符，逐组件使用 `dir_fd` 和 `O_NOFOLLOW`。文件必须是普通文件且没有多重硬链接，内容还受大小、编码和控制字符检查。读写前后重新核对根目录及祖先位置与 inode，写后重新打开验证内容。测试覆盖最终链接交换、目录移动、硬链接、路径编码和拒绝消息不泄露 OS 私有路径。

仍不能把它称作 OS sandbox。恶意原生进程若拥有同一 OS 身份，可以在检查和 syscall 的微小窗口内继续改名或改内容；完整防护需要权限隔离或系统机制。文件名过滤也识别不了所有秘密，授权目录应只包含允许交给模型的数据。

追问：为什么禁止整个 home 和仓库根目录？这些范围通常包含密钥、环境变量文件、版本控制元数据与其他项目；把根目录缩到专门的演示或授权子目录，能让权限与预期操作更容易审查。

## 8. HITL 如何体现？`--approve-writes` 会不会绕过沙盒？

默认写入返回预览及 `written=false`，磁盘不发生写操作。操作者的 `--approve-writes` 是对当前授权目录写操作的预先批准；不是逐次弹窗确认。即使获准，路径与资源限制仍照常执行。

覆盖普通文件还需要两个条件：操作者 `--allow-overwrite`，以及该次工具参数 `overwrite=true`。二者分别代表操作者授予能力与调用明确使用该能力，缺一就拒绝。CLI 不允许没有写批准却开启覆盖选项。

todo 使用保留状态文件。批准新增或完成动作，只授权修改格式标记正确的自身状态；未知的原有内容不会被替换，普通 `write_file` 也不能写入这一保留路径。新增与完成在未批准时同样只返回预览。

追问：预先批准适合哪些任务？适合范围明确、示例数据可丢弃、工具能力受限的无人值守演示。高风险业务应缩小批准粒度并加入独立确认机制；当前实现不宣称覆盖这种生产审批场景。

## 9. Token 与时间预算能精确控制费用吗？

不能把本地计数当作供应商账单。运行时在请求前根据消息与 Schema 的 UTF-8 JSON 字节数进行保守估算，预留输出 `max_tokens`，并检查总预算；返回后优先记录有效的 provider usage，缺失 usage 时记估算值。非 Mock 请求报错或超时，也记不确定请求的估算消耗，避免重试看起来不消耗预算。

`token_charges` 保留消耗来源，离线 Mock 的零消耗也明确标记。字节估算没有调用目标模型 tokenizer，provider usage 又是事后信息，所以只能抑制失控调用，不能证明精确计费或绝对费用上限。

时间方面使用单调时钟、模型异步超时和工具子进程终止。工具 fork 后端针对 Linux/WSL；直接搬到原生 Windows 需要新的进程执行方案，不能假设行为相同。

追问：为什么只给网络请求 timeout 不够？一轮可能包含多个工具和重复模型请求，还需要总运行时长、总调用数、最大轮数与重复检测，才能限制组合后的消耗。

## 10. 如何证明产物来自材料？Prompt Injection 是否已彻底解决？

证据链从真实工具开始：搜索返回相对路径，读取返回正文与 SHA-256，脚本从本轮实际 read observation 中提取内容；写工具确认文件存在、内容与预期一致后返回 `written=true` 和 hash。工具与离线演示明确区分预览和落盘；真实模型的自然语言仍可能出错，应以工具证据为准。端到端测试验证最终文件包含已读来源，并包含笔记内容变化后的真实证据。

离线学习计划使用确定性的原文提取，标注来源、职责句和差异/关系原文；材料没有写明的内容不会冒充已推断结论。这验证数据链路，不代表通用语义分析质量。

文件中的“忽略系统策略”“读密钥”等文字保留为不可信数据。系统策略声明这个边界，工具层仍独立拒绝敏感路径，且根本没有 shell 或任意网络工具。注入测试验证恶意材料不能授予权限或触发额外操作；真实模型仍可能生成错误摘要或不当工具请求，系统指令本身不是彻底的注入防护证明。

追问：hash 能证明结论正确吗？不能。它标识工具实际读写的字节，可用于核对来源与内容一致性；是否忠实概括、来源是否可信、文件后来是否改变，仍需额外验证。

## 扩展讨论：为什么没有引入 Agent 框架？

项目希望直接展示 function calling、状态转换、权限和错误边界，因此核心 Loop 没有依赖 LangGraph 或 OpenAI Agents SDK，也没有附加这些框架的适配实现。它们可作为未来复杂图分支、检查点或观测机制的选项；引入后需要评估额外依赖与抽象层，同时保留当前工具校验、沙盒与写入证据。
